# Teach Aside to understand everything said

Aside does not work out what "the question" is. When you press Command+Enter, it takes **everything both people said since your last press**, sends all of it to one AI model along with a long rulebook and your resume and job description, and asks "what should I say next?". The AI is told to spot every question, answer them together, and treat small talk and plain information differently. It makes all of those decisions silently, inside the same request that writes the answer, and **nothing about them is written down**. The question shown above the answer comes from a single line of code that **picks the last sentence the other person said**. That is the whole reason only the last question appears when several were asked: the AI may well be answering all of them, but the label is chosen separately and without looking at them. Research and the strongest competitors point the same way. Natively (ideas only; its licence forbids reusing its code or prompt wording) and the academic work on understanding conversations both say to add a small, fast "listener" step. It labels each stretch of speech with one of about eight practical types, rewrites follow-ups and multi-part questions into one clear question, keeps a running list of open questions and facts the other person shared, and passes all of that to the answering step. The recommended plan has five phases. The first, a combined-question label written by the same AI call that writes the answer, fixes the "only the last question" complaint in days and adds almost no delay. Later phases add the listener, a different response for each type of speech, a structured personal profile, and speed work. Every part of the plan below is **DESIGNED — UNBUILT**. Facts about today's Aside come from reading the code on branch `redesign-dock`; nothing was run live for this report.

A note on the two comparison projects. The project rules ask that each feature be checked against `references/Repo1-Natively` and `references/Repo2-OpenCluely`. Those folders **do not exist** in this checkout: `references/` holds a different Electron app called "Assistant". Natively and OpenCluely were therefore read from their public GitHub pages.

## Aside answers a bucket of speech, then labels it with one line

### How it works today, in plain words

Think of a bucket. Every sentence you and the other person say drops into it, each tagged "Me" (your microphone) or "Other" (the call audio). When you press Command+Enter, Aside empties the bucket into one request to the AI model. The request contains three things. First, a rulebook of 58 rules and 6 worked examples. Second, your documents: Guidance notes, company, job description, resume and any other files. Third, a short running summary of earlier parts of the call, followed by the bucket's contents. The AI streams back an answer, and the live window shows it under a heading. Pressing again with nothing new said re-uses the same bucket. Typed follow-ups and screenshots use the same machinery with a one-line stand-in for the conversation ([window_memory/mod.rs:1-4, 106-121](../src-tauri/src/window_memory/mod.rs); [llm/mod.rs:1038-1067](../src-tauri/src/llm/mod.rs)).

So all the "understanding" is done by the AI, out of sight. Aside's own code does almost none. It has no step that decides "this was a question", "these were two questions", "this was just information" or "this is a follow-up to what we discussed five minutes ago". The rulebook asks the AI to make those calls, but the answer comes back as plain text with no record of what it decided ([window_memory/prompt.rs:11-19, 97, 169-172](../src-tauri/src/window_memory/prompt.rs)). Because nothing is recorded, the app cannot show the decision, cannot remember that question 3 is still unanswered, and cannot link a follow-up to the question it follows.

### Why only the last question shows up

Three separate pieces of code each keep only the latest question.

The first, and the main one, is the heading above the answer. A short piece of code walks backwards through the bucket, takes **the last line the other person said**, and uses that as the heading ([llm/mod.rs:1170-1180](../src-tauri/src/llm/mod.rs)). If the interviewer said "Tell me about your current project", paused, then said "And what do you expect from this position?", the heading reads "And what do you expect from this position?". That happens even though the rulebook explicitly tells the AI to answer both questions in order, using almost exactly this example ([window_memory/prompt.rs:151-155](../src-tauri/src/window_memory/prompt.rs)).

Second, there used to be a way for the AI to write a cleaned-up question. An older rulebook told it to start with a "Q:" line and then an "A:" line, and a helper split the two apart. The current rulebook forbids any extra lines ("plain text I can say out loud — nothing else"), and the Command+Enter path no longer uses the splitting helper, so **no combined question is ever produced** for Command+Enter answers ([llm/question_split.rs:19-78](../src-tauri/src/llm/question_split.rs); [llm/mod.rs:633-718](../src-tauri/src/llm/mod.rs); [Reading.tsx:21](../src/live/parts/Reading.tsx)).

Third, the "Question detected" card in the live window replaces its question each time the other person says something that looks like a question. It keeps only the newest fragment, even when the screen has joined that fragment into a longer line ([src/live/machine.ts:184-198](../src/live/machine.ts)).

Two smaller effects add to the problem. Aside's speech-to-text service ends a sentence after **0.6 seconds of silence**, so an interviewer who pauses briefly mid-question produces two separate lines, and the second half becomes "the question" ([stt/speechmatics.rs:88-89](../src-tauri/src/stt/speechmatics.rs)). And when the same person says two lines whose words overlap by 60% or more, Aside keeps only the later one. That is usually fine for a corrected question, but "How big was the team?" followed by "How big was the budget?" share enough words to be merged into one ([window_memory/live.rs:48-65](../src-tauri/src/window_memory/live.rs); [conversation/similarity.rs:41-50](../src-tauri/src/conversation/similarity.rs)).

There is also a contradiction inside the rulebook. Rule 2 says never to answer only the final sentence. Rule 55 says to classify the interviewer's *most recent turn* and let that decide the answer's shape and length ([window_memory/prompt.rs:9, 97](../src-tauri/src/window_memory/prompt.rs)). Nobody has measured whether the AI really answers every question when several are asked; no test or recorded run checks it.

The rest of the gap is about memory, follow-ups and personalisation. Most of it is structural, so rewording the rulebook will not fix it.

### Technical detail (for the engineer)

The hot path is `shortcuts::answer_current_question` → `llm::respond_to_window` → `window_memory::freeze_for_answer` → `build_request_with_length` → OpenAI Chat Completions streaming via `WindowAnswerSink` → `answer-started`/`answer-delta`/`answer-done` events → `src/live/machine.ts` → `Reading.tsx`. The prompt's `system` part is `STRICT_RULES` (or the Settings override) plus `DefaultContext::render()`, plus the length override when Short/Med/Long is pressed. The `user` part holds the Known Facts, the summaries, then the raw window as `Other:`/`Me:` lines ([window_memory/prompt.rs:555-577](../src-tauri/src/window_memory/prompt.rs)). The default answer model is `gpt-5.6-luna` with `reasoning_effort: "none"`; the background summariser is `gpt-5.4-mini`, and a stable `prompt_cache_key` is sent ([llm/openai.rs:24-98, 153-169](../src-tauri/src/llm/openai.rs)). Nothing is prefetched; the request starts at the key press, and speed comes from including live interim words, a pre-warmed connection and prompt caching ([window_memory/live.rs:186-208](../src-tauri/src/window_memory/live.rs); [llm/mod.rs:719-760](../src-tauri/src/llm/mod.rs)). The "Assistant" app in `references/` also has no question classifier. It answers "everything since the last press, other person only", adds up to 180 seconds of earlier raw transcript as background, keeps earlier answers in history, and has an explicit "continue the previous answer" action ([references/src/main/services/TranscriptStore.ts:77-115](../references/src/main/services/TranscriptStore.ts); [ChatService.ts:47-85](../references/src/main/services/ChatService.ts)).

## The best competitors put a small, fast judge in front of the answer

### What the open-source projects do

The open-source copilots fall on a ladder. At the bottom, **Pluely** (a Rust/Tauri app like Aside) sends every utterance after about a second of silence straight to the AI with no question filter ([useSystemAudio.ts](https://github.com/iamsrikanthnani/pluely/blob/master/src/hooks/useSystemAudio.ts)). **OpenCluely** collects speech fragments for 800 milliseconds and sends whatever piled up. If several questions arrive back to back they are merged into one blob, and small talk is handled only by a rule telling the AI to reply "I'm listening" ([main.js](https://github.com/TechyCSR/OpenCluely/blob/main/main.js); [llm.service.js](https://github.com/TechyCSR/OpenCluely/blob/main/src/services/llm.service.js)). **Cheating Daddy** streams audio to Google's real-time model and lets the model itself decide whether to speak ([gemini.js](https://github.com/sohzm/cheating-daddy/blob/master/src/utils/gemini.js)). **Glass** and the leaked **Cluely** prompt answer "the current moment", meaning the end of the transcript. They work down a fixed order: answer a recent question, else define a term just mentioned, else solve what's on screen, else say "not sure what you need" ([Glass promptTemplates.js](https://github.com/mickaelleclercq/glass/blob/main/src/features/common/prompts/promptTemplates.js); [Cluely prompt, unverified leak](https://github.com/x1xhlol/system-prompts-and-models-of-ai-tools/blob/main/Cluely/Enterprise%20Prompt.txt)). Aside's approach, with the whole bucket and a rulebook in one call, sits in this middle group.

**Natively** is clearly the most advanced. Its design is worth studying for ideas, though its licence names prompts and ports as covered material, so no code or wording can be copied ([LICENSE](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/LICENSE)). It works in stages. It waits for the interviewer to stop. It runs a free local filter that drops "yeah", "got it" and very short fragments. Then it asks **one small, fast AI "judge" exactly once per pause**: is this a complete request, is it aimed at the user, what kind is it, and what exactly is the question. The judge must return the question quoted from what was said, covering *every part* of a multi-part request. If fewer than 65% of the quoted question's words actually appear in the speech, the app treats the quote as invented and falls back to the raw speech ([AutoAnswerJudge.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/intelligence/autoAnswer/AutoAnswerJudge.ts)). The judge's rules list what is *not* a question: explanations and thinking aloud, a question the speaker answers themselves, permissions like "take your time", logistics like "share your screen", "we'll come back to that", and "…, right?" tags. A task stated as a sentence ("your task is to build this game") counts as a question. Questions the *user* asked, and questions addressed to someone else by name, are left alone. When the speaker has announced "two parts" and delivered only one, the judge marks it unfinished and waits ([AutoAnswerJudge.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/intelligence/autoAnswer/AutoAnswerJudge.ts)).

Natively's lessons are as useful as its design. Its authors report that six rounds of more complicated detection machinery "ate" real questions, and that the simple version won: wait for a stop, judge once, discard the judgment if the speaker resumes ([SimpleAutoAnswer.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/intelligence/autoAnswer/SimpleAutoAnswer.ts)). They removed a "press Tab to get an answer" card because asking permission costs a keystroke at the worst moment, and they now lean towards answering when in doubt. They found the judge's speed depends mostly on how much text it reads: about **1.0 second at 2,000 tokens, 1.6 seconds at 7,500, and 3.8 seconds at 28,000**, so they feed it only the last 8 turns, keeping the *ends* of long turns because a request lands at the end of speech ([AutoAnswerJudge.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/intelligence/autoAnswer/AutoAnswerJudge.ts)). They also found, by measurement, that the judge works better with its instructions placed *after* the transcript. Putting merged multi-turn requests after the instructions dropped from 3 of 3 caught to 0 of 3 ([AutoAnswerJudge.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/intelligence/autoAnswer/AutoAnswerJudge.ts)). For follow-ups, separate code turns fragments like "And SQL?" or "Why?" into full questions borrowing the previous subject. Longer-range memory lets "that project" at minute 62 resolve to something said at minute 1 ([FollowUpResolver.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/llm/FollowUpResolver.ts); [sessionFollowupResolver.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/llm/sessionFollowupResolver.ts)). A fixed priority decides what to answer: something you typed beats a line you clicked, which beats the latest interviewer question, which beats a follow-up worked out from context ([question-resolver.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/context-intelligence/question/question-resolver.ts)).

Even Natively does not show several separate open questions live. Its "question ledger" names exactly Aside's problem, that the latest question wins so earlier unanswered ones vanish and compound questions collapse, but it only **records in the background and does not drive answers yet** ([questionLedger.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/llm/questionLedger.ts)). Showing every open question would set Aside apart.

### What commercial products show

Paid interview copilots split into automatic detection and manual triggering. Reviewers credit two-channel audio (the other person's audio kept separate from your microphone) as the main reason automatic detection works, because it shows who spoke. Final Round, Verve, Sensei and LockedIn are described as working this way ([Vizologi roundup](https://vizologi.com/7-best-ai-interview-assistants-for-coding-2026-update/)). Aside already has both channels. The complaints are specific. Parakeet users report missing **a question that comes at the end of a long statement** ([Parakeet feedback board](https://parakeetai.featurebase.app/p/the-ai-is-unable-to-detect-questions)). Final Round users report misread questions, several answers at once, and answers scrolling too fast to read ([Trustpilot](https://au.trustpilot.com/review/finalroundai.com?page=4)). LockedIn is criticised for 4–5 second delays that read as hesitation ([CloudColleague](https://cloudcolleague.com/blogs/interview-tips/lockedin-ai-review/)), and Cluely users saw 5–10 second delays and invented facts, such as a language the user never spoke ([Medium](https://medium.com/@wenhaooyang/cluely-i-tried-the-ai-that-cheats-for-you-in-meetings-a53a89c01d56)). Most of these sources are small samples, and some come from competitors. No independent accuracy benchmark exists for any of these products. Meeting assistants like Microsoft Teams Copilot don't answer live, but Teams offers a ready-made prompt asking which questions were asked, answered and left unresolved. That is the closest commercial version of an open-questions list ([Microsoft Support](https://support.microsoft.com/en-us/office/use-copilot-in-microsoft-teams-meetings-0bf9dd3c-96f7-44e2-8bb8-790bedf066b1)).

On personalisation, the products go beyond a pasted resume. Sensei has a bank of prepared stories, Verve has prepared question-and-answer pairs, Natively Pro offers company research files, and MeetingCopilot and meetingly-ai keep a running memo of lasting facts from the call ([Vizologi](https://vizologi.com/7-best-ai-interview-assistants-for-coding-2026-update/); [MeetingCopilot prompts.ts](https://github.com/JWM0203/MeetingCopilot/blob/main/electron/llm/prompts.ts); [meetingly-ai suggestions.ts](https://github.com/iskandaryv/meetingly-ai/blob/main/app/electron/services/suggestions.ts)). On display, the good patterns show the detected question above the answer so you can catch a mishearing, and let you click a transcript line to choose what to answer ([Cue prompts.js](https://github.com/Blueturboguy07/cue/blob/main/src/prompts.js); [Cheating Daddy prompts.js](https://github.com/sohzm/cheating-daddy/blob/master/src/utils/prompts.js)). Answers converge on a short first line you can say immediately, then a few short points: Cluely and Glass use a headline of six words or fewer, Natively uses 2–4 spoken sentences.

## Research favours a short list of speech types, rewritten follow-ups, and layered memory

### Use about eight practical types, not fifty linguistic ones

Researchers call the job of labelling each piece of speech "dialogue act" tagging. The academic schemes use 40–50 fine-grained types, and on those, general AI models do poorly. A 2025 study found that on a 50-type, many-speaker scheme they often fail to beat simple rule-based methods, with a significant gap to human understanding ([Qamar et al., ACL 2025](https://aclanthology.org/2025.acl-long.1271/)). A model trained specially for the task scored 62.5% against 51.1% for GPT-4 given a few examples ([arXiv 2410.23535](https://arxiv.org/pdf/2410.23535)). The lesson for Aside is to label speech by **what the copilot should do with it**, not by grammar, and to keep the list short. Aside also gets "who spoke" free from its two audio channels, which removes the turn-taking problem the 2025 study found hardest for AI models. Research on spotting questions in meeting speech found that the words and sentence shape matter most, with pauses and pitch adding a little ([Boakye et al., ASRU 2009](https://experts.illinois.edu/en/publications/any-questions-automatic-question-detection-in-meetings/)). Transcription errors hurt a lot: one classroom study managed only 59% accuracy (F1 0.59) at spotting teacher questions from noisy transcripts ([W16-3623](https://preview.aclanthology.org/author-url/W16-3623.pdf)). So Aside should not trust question marks in the transcript. Requests like "walk me through…" carry no question mark at all.

### Several questions at once is a solved-enough problem for large models

Research on sentences that carry several requests at once ("multi-intent") shows large AI models are now "competitive, if not outright superior" to purpose-built systems ([arXiv 2403.04481](https://arxiv.org/html/2403.04481v4)), even though the hardest test sets remain difficult: the best specialised system reaches 59% overall accuracy on one of them ([arXiv 2312.05741](https://arxiv.org/pdf/2312.05741)). No published dataset covers combining several interview questions said across separate turns, so Aside will have to measure this itself.

### Follow-ups should be rewritten into stand-alone questions

The established technique for "and why did you choose that?" is *query rewriting*: turn the fragment into a complete question using the recent conversation. AI rewrites have beaten human rewrites when used to search for relevant material ([Ye et al., EMNLP Findings 2023](https://arxiv.org/pdf/2310.09716)). That matters directly for Aside. A rewritten question is something the answer step can use, the screen can show, and a document search can look up.

### Knowing when the speaker has finished

Speechmatics, Aside's speech-to-text service, ends an utterance purely on silence, adjustable from 0 to 2 seconds. It also lets an app force an end early when it has its own reason to think the speaker is done ([Speechmatics docs](https://docs.speechmatics.com/speech-to-text/realtime/end-of-turn)). Aside uses 0.6 seconds, which is quick but splits questions at natural mid-sentence pauses. Newer "end-of-turn" models judge whether someone has *finished their thought*. Pipecat's open-source Smart Turn v3 reads the audio and runs in about 12 milliseconds on an ordinary computer chip, in the same ONNX format Aside already uses for its local speech engine ([Daily](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)). LiveKit's text-based model catches finished turns 98.8% of the time and unfinished ones 87.5% of the time ([LiveKit docs](https://docs.livekit.io/agents/logic/turns/turn-detector)). Voice-agent builders start drafting a reply on an early "probably finished" signal and throw it away if the speaker carries on. Deepgram says this costs about **50–70% more AI calls** ([Deepgram](https://developers.deepgram.com/docs/flux/voice-agent-eager-eot)).

### Memory should be layered, and written in the background

Research on AI memory, from MemGPT's "memory hierarchy" to Mem0 and Zep, converges on the same design. Extract the important facts, merge them with what is already known, and mark outdated facts as replaced instead of piling them up ([MemGPT](https://arxiv.org/abs/2310.08560); [Mem0](https://arxiv.org/abs/2504.19413); [Zep](https://arxiv.org/html/2501.13956v1)). These are large multi-session systems, and other vendors dispute Mem0's benchmark numbers ([review](https://rywalker.com/research/mem0)). Aside should borrow the ideas, not the software. LangChain's guidance adds that writing memory in the background, off the answering path, keeps answers fast at the cost of slightly later updates ([LangChain](https://docs.langchain.com/oss/python/concepts/memory)). Where information sits in the prompt also matters. AI models use material at the start and end of their input best and the middle worst, and accuracy falls as input grows ([Liu et al., Lost in the Middle](https://arxiv.org/abs/2307.03172v3)). That argues for putting the current question last and keeping the prompt lean. Anthropic's guidance agrees: a few good examples teach better than long lists of rules, and you should add instructions only to fix observed failures ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Aside's 58-rule prompt runs against that advice.

### Personal material is small enough to include whole, with grounding rules

A resume, a job description, company notes and a set of stories add up to a few thousand tokens. Anthropic says anything under about 200,000 tokens can simply be put in the prompt, and prompt caching makes that more than twice as fast and up to 90% cheaper ([Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)). OpenAI caches a prompt's opening automatically once it is at least 1,024 tokens. On GPT-5.6 and later, cached input costs a tenth of the normal price and stays warm for at least 30 minutes after last use, but any change to the opening, even one character, loses the cache ([OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). To stop the AI inventing experience, Anthropic's guidance is to explicitly permit "I don't know", limit answers to the supplied documents, and tie claims to sources ([Anthropic, Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)).

## The redesign: a listener that writes down what each thing said is

### The idea in plain words

Today one AI call does both the listening and the answering, and leaves no notes. The redesign splits those jobs. A **listener** runs quietly in the background as the conversation happens. After each time the other person stops talking, it writes a small note: what kind of thing was just said, the question rewritten so it makes sense on its own, which earlier question it follows up on (if any), and any facts worth remembering. It keeps a running **open-questions list** and a **notebook** of what the other person has told you and what you have already said. When you press Command+Enter, the **answerer** gets the notes as well as the raw speech. It knows exactly which questions to answer, in what order, and in what form, and the screen shows the combined question instead of the last sentence.

Your press stays in charge. The owner removed automatic answering in August ([docs/decisions.md:49-51](../docs/decisions.md)), and the plan keeps the manual press as the main trigger. The listener only makes the press smarter and faster, and if its note isn't ready the press still works exactly as it does today.

### How each type of speech should be handled

| What was said | Example | What Aside should do |
|---|---|---|
| A question or request | "Walk me through your resume." | Answer in your voice, from your profile |
| Several questions | "Tell me about your project… and what do you expect from this role?" | Show one combined question; answer in numbered parts, in order |
| One question with several parts | "What was the problem, what did you do, and what was the result?" | Keep it as one question; answer every part; wait if a promised part hasn't come yet |
| A follow-up | "Why that approach?" | Rewrite it as a full question; build on the answer you actually gave, keep the same numbers and story, add depth |
| Information or context | "We're a team of six and run everything on Kafka." | No full answer. A one-line "Noted" card linking it to your profile ("ties to your Kafka project"), saved for later answers |
| Clarification | "Do you mean the API or the database?" | A short line to say, or suggest a clarifying question back |
| Small talk | "How's your day going?" | One warm, natural line under about 15 words |
| Logistics | "Share your screen." "We have 20 minutes left." | Nothing, or a quiet note |
| Your own speech | You answer, or ask the interviewer something | Never answered; marks questions as "being answered" and records what you claimed so later answers stay consistent |

This list is adapted from the dialogue-act research, Natively's list of things that are not questions, and the policy design in the personalisation research. **No published study defines the "right" types for an interview copilot**, so these will need tuning against real recordings. One rule should override everything else. When the listener is unsure whether something is a question, it should treat it as one, because a missed question hurts far more than an extra answer you can ignore. Natively reached the same conclusion after live testing ([AutoAnswerJudge.ts](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/electron/intelligence/autoAnswer/AutoAnswerJudge.ts)).

### What the screen should show

For several questions, show the combined question as the heading ("Your current project, and what you expect from this role"), with the answer in matching numbered parts. In a later phase, a small open-questions list sits above it. Items are ticked off as they are answered, and clicking one re-aims the answer at it. That follows Natively's priority order (what you type or click beats what the app guesses), and it goes one step further than any product reviewed, since none shows a live list. Answers should open with one sentence you can say straight away, followed by two to four short points. Behavioural questions should use a compact Situation–Task–Action–Result story drawn from *your* stories, with a real number in the result. Career guides suggest such answers take about 90 seconds to 2 minutes to say ([Glassdoor STAR guide](https://image4.glassdoor.co.in/blog/guide/star-method/)). These are career-blog sources, not research.

### A personal profile instead of pasted documents

Personalisation should move from "paste the documents" to a **structured profile** built once per copilot and reviewed by you. It would list your roles, projects with real numbers, skills, a bank of 10–20 stories tagged by theme (conflict, failure, leadership), the job's requirements matched to your evidence, the target role, and company facts. Each item gets a short ID such as S7 or R2. The whole profile fits comfortably in the prompt and in the cache, so nothing gets cut at 6,000 characters and no story is missed by a search. The answerer is told to claim only experience that appears in the profile and to say so honestly when a question asks for experience you don't have. Aside's own code can then check, cheaply, that any number in an answer appears somewhere in your profile. During the call, the listener's notebook records facts the interviewer shares, the claims and stories you've already used, and the current phase (intro, behavioural, technical, your questions). That way answers stay consistent and don't reuse the same story. After the call, your claims carry over so a second-round interview stays consistent with the first. A small "too long / not me" feedback button with two or three of your approved answers saved as examples would teach style better than more rules, in line with Anthropic's advice on examples.

### Technical detail (for the engineer)

**Listener output.** Use one fixed strict JSON schema, with the fields that drive decisions first so a streaming parser can act early. A sketch:

```json
{
  "kind": "question|request|multi_question|follow_up|clarification|context|small_talk|logistics|none",
  "complete": true,
  "action": "answer|note_context|ignore|wait",
  "confidence": 0.0,
  "questions": [{"id": "q4", "text": "self-contained rewrite", "type": "behavioral|technical|resume|logistics|other", "refers_to": "q2|null", "quote": "verbatim span"}],
  "consolidated": "one combined question or null",
  "context_notes": ["team of 6", "uses Kafka"]
}
```

Check each `quote` against the transcript, borrowing Natively's idea of an overlap check rather than its code. If too few words match, display the raw lines instead of the rewrite.

**Where it runs.** In Rust, trigger it on each final "Other" utterance (Speechmatics `EndOfUtterance`). Debounce so there is one call per pause, never one per fragment, and drop the result if new "Other" speech arrived while the call was in flight. Feed it a bounded input: the current open-question list, the last ~8 turns with long turns cut from the front, and the last few question/answer summaries. That keeps it near the ~2,000-token size Natively measured at about one second. Put its short task instructions *after* the transcript, as Natively measured. Store the results in a per-session state row: open questions with status, interviewer facts with superseded-by links, user claims with profile IDs, topics covered, and phase. Finally, populate the existing but never-written `interview_exchanges` table rather than inventing a new one ([storage/exchanges.rs](../src-tauri/src/storage/exchanges.rs)).

**Press path.** `respond_to_window` reads the latest listener state without waiting more than a short timeout (suggested ≤300 ms, to be tuned). It sends `answer-started` with `consolidated`, or the joined open questions, instead of the last "Other" line, and adds a short "QUESTIONS TO ANSWER, IN ORDER" block plus "facts shared" at the end of the user message. The raw window stays in, so the answerer can still catch what the listener missed. If listener state is missing or stale, fall back to the Phase 1 behaviour below.

**Prompt layout for caching.** Keep the order stable from the top down: fixed rules and examples, then the style profile, then the copilot profile serialised deterministically with IDs. That is the cache boundary, and it is reused for the whole session. Then the session state and rolling summary, then recent raw transcript, then the current questions last. Prewarm the prefix at session start. This keeps OpenAI's cache hitting while still putting the question at the end, where Lost in the Middle says it belongs. The listener has its own small fixed prefix and never touches the answer path's cache key.

### Phase 0 and Phase 1 in more detail

The bug fixes in Phase 0 are small and each closes a gap found in the code. The typed-question path waits for an "A:" marker the rules forbid, so it should stop waiting. A corrected fact should *replace* the old one in memory, not sit beside it. Facts heard during the call should reach the AI without waiting for some unrelated reload. The 60%-word-overlap merge should only fire when one line clearly restates the other, so that "team size" and "budget" questions stay separate. The stale comments and the decisions-note mismatch should be corrected. The test bench should cover the hard cases deliberately: mid-question pauses, requests with no question mark, rhetorical "right?", stacked questions, a question at the end of a long explanation (Parakeet's named failure), follow-ups that need history, small talk, information monologues, and you speaking over the interviewer. Aside's existing Speechmatics fake server and replay work makes exact replays practical ([stt/speechmatics_live/fake_server.rs](../src-tauri/src/stt/speechmatics_live/fake_server.rs)).

Phase 1 deliberately uses the *same* AI call rather than a second one. That way the heading and the answer can never disagree, and no extra request is waiting. Aside already contains the splitting machinery from the old "Q:/A:" design, so the work is mostly re-pointing it ([llm/question_split.rs](../src-tauri/src/llm/question_split.rs)). The "Assistant" reference app uses the same trick for answer length, emitting a hidden tag first that the app strips ([references/src/shared/answerLength.ts](../references/src/shared/answerLength.ts)). The alternative is a separate cheap call running alongside the answer to write the heading. That leaves the answer prompt untouched, but the label could describe something the answer didn't cover. It is the fallback if the in-call heading proves unreliable.

### How to know it works

Score each phase against the replay set before and after. For labelling, measure how often each type is recognised correctly, watching above all the two costly mistakes: a real question treated as "ignore", and plain information treated as a question. For multiple questions, check that the number of questions found matches the real number. Rate the combined heading for being correct, complete, self-contained and not repetitive, the four qualities the query-rewriting research uses ([Ye et al.](https://arxiv.org/pdf/2310.09716)). For speed, measure time from press (or from the interviewer stopping, in Phase 5) to the first visible word. Reviewers treat **about 1–2 seconds as acceptable and 4–5 seconds as damaging**, and Natively's own benchmark shows about 0.85 seconds to first text at the median once triggered ([Natively latency runs](https://github.com/Natively-AI-assistant/natively-cluely-ai-assistant/blob/main/benchmarks/natively-answer-quality/astra/out/latency/existing-runs.md)). For cost and caching, log OpenAI's reported cached-token counts on each request. Then run a handful of real practice calls, since replayed scripts never capture everything. Following the project's quality bar, each phase is called **BUILT + VERIFIED** only after the replay scores and a real call have been checked and recorded in `docs/evidence.md`.

### Risks and how to contain them

The biggest risk is **the listener missing a real question**. The containment is the "when unsure, it's a question" rule, the raw speech staying in the answer prompt, and the press always producing an answer. The second risk is **over-engineering**: Natively's six rounds of clever machinery losing questions is a direct warning, so each phase should stay simple and prove itself on the test set before the next begins. The third is **an invented heading or answer**, contained by the quote check, the grounding rules and the number check. A fourth is **cost creep**, mainly from speculative drafting in Phase 5. Only draft when the listener is confident and the action is "answer", and leave speculation off by default. A fifth is **breaking the prompt cache** by putting anything that changes, such as the time or the rolling summary, in the stable opening. A sixth is **privacy**: more structured memory means more personal data on disk, and every answer still sends your profile and the transcript to OpenAI, which keeps a processed form briefly to speed up later requests ([OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). The profile should leave out contact details, and per-copilot deletion and a "don't save transcript" option should come with Phase 4. The last is **licensing**. Natively's ideas can guide the design, but no code or prompt text from it may be used, and GPL projects (Cheating Daddy, Pluely, Cue, Glass) would force their licence onto copied code. Rollback is simple for every phase: each sits behind the existing answer path, which keeps working if the new part is switched off.

## Conclusion

The striking finding is that Aside's main complaint isn't an AI problem at all. The model is already shown every question and told to answer them all. A single line of display code throws that away, and the design never asks the model to say what it understood. So the cheapest, highest-value fix is to make the understanding *visible*: once there is a written record of what was said and what it means, the heading, the open-questions list, follow-up handling, "Noted" cards and personal consistency all become things the app can show and check, rather than hopes buried in a 58-rule prompt.

The research also changes what "smarter" should mean. The field's evidence favours fewer, practical speech types over rich linguistic labels, a small background listener over one giant prompt, and a structured profile kept whole in a cached prompt over document search. Above all, it favours ruthless simplicity, because complex detection tends to lose the very questions it was built to catch. If Aside ships the combined heading first, proves each later phase on a replayable test set, and becomes the first copilot to show a live list of open questions, it moves from "answers the last thing said" to a copilot that genuinely follows the conversation, without giving up the manual control the owner chose.
